# 拍照饮食分析小程序 MVP 需求文档

## 1. 项目目标

做一个微信小程序，用户拍照上传一桌饭菜后，系统自动识别画面中的食物，在图片上标出菜品位置，并分析这顿饭的大致热量、营养风险、菜品成本和适合的吃法。

第一版重点验证：**拍照识别 + 热量估算 + 成本估算 + 个性化饮食建议**。

## 2. 核心功能范围

### 2.1 拍照识别

- 支持用户拍照或从相册选择图片。
- 调用千问视觉模型识别图片中的菜品。
- 返回每个菜品的：
  - 菜品名称
  - 坐标框
  - 识别置信度
  - 可能食材
  - 可能烹饪方式
  - 份量估算

### 2.2 图片标注展示

- 前端在原图上展示菜品坐标框。
- 点击坐标框或菜品卡片，可查看该菜品详情。
- 用户可对图片进行缩放和拖拽查看局部细节。
- 图片缩放或拖拽时，菜品坐标框必须跟随图片同步缩放、移动，保持与原图目标位置一致。
- 用户点击图片某个位置时，可围绕该位置进行局部放大，方便查看小菜、配料或被遮挡区域。
- 用户可删除明显误识别的菜品。
- 用户可手动修改菜名。

### 2.3 热量与营养分析

- 根据识别结果估算：
  - 单个菜品热量范围
  - 整桌总热量范围
  - 碳水、脂肪、糖、钠风险
- 所有营养结果必须显示为估算，不给绝对确定值。
- 结果应包含置信度或“不确定”提示。

### 2.4 菜系与餐型识别

- 每次分析时，系统需要判断这一桌饭菜大致属于什么菜系或餐型。
- 识别维度包括：
  - 家常菜
  - 淮扬菜
  - 川菜
  - 粤菜
  - 湘菜
  - 火锅
  - 干锅
  - 烧烤
  - 快餐/简餐
  - 西餐/日料/韩餐等其他类型
- 判断依据包括：
  - 单道菜名称
  - 多道菜组合
  - 烹饪方式
  - 锅具、餐具、汤底、蘸料等视觉线索
  - 辣度、油量、汤汁、摆盘等画面特征
  - 用户选择的餐厅 POI 类目和店铺标签，可选
- 返回内容包括：
  - 主分类，例如“火锅”“家常菜”“淮扬菜”
  - 可选副分类，例如“川味火锅”“江浙家常菜”“干锅类”
  - 分类置信度
  - 判断依据说明
- 如果画面混合多种菜系，应返回“混合餐型”并列出可能类型，不强行归为单一菜系。
- 菜系与餐型识别结果应参与后续热量、成本和健康建议分析。例如火锅、干锅通常需要重点提示油脂、钠和蘸料摄入。

### 2.5 菜品成本估算

- 根据菜品识别结果、可能食材、份量、烹饪方式和用餐场景，估算这桌菜的大致成本。
- 成本估算分为两类：
  - **食材成本**：如果用户选择在家吃、食堂或未选择餐厅，估算这桌菜在家制作所需的大致食材成本。
  - **餐厅消费参考**：如果用户选择餐厅、外卖或自行填写店名，结合 POI 人均、店铺类型、公开摘要和菜品类型，估算合理消费区间。
- 返回内容包括：
  - 单个菜品成本范围
  - 整桌菜品成本范围
  - 成本置信度
  - 成本判断说明
  - “偏贵 / 正常 / 偏便宜”参考结论，可选
- 成本结论必须使用范围值，例如 `28-42 元`，不能输出绝对成本。
- 成本估算只作为参考，不作为真实采购价、真实售价或商家定价依据。
- 如果缺少城市、店铺、人均或份量信息，应明确提示“成本估算不确定”。

### 2.6 个性化健康建议

- 用户可本地填写健康备注：
  - 糖尿病
  - 控糖
  - 减脂
  - 高血压
  - 忌口
  - 健身增肌
- 使用 DeepSeek V4 Flash 生成饮食建议。
- 建议口径必须谨慎：
  - 可以说“建议少量食用”
  - 可以说“建议主食减半”
  - 可以说“油脂/钠/碳水可能偏高”
  - 不可以说“你不能吃”
  - 不可以替代医生诊断

### 2.7 用餐地点与餐厅信息

- 用户拍照后，系统可请求定位权限，但用户可以拒绝或跳过。
- 如果用户授权定位，后端调用地图 POI 接口，返回附近 3-5 家餐饮店候选。
- 餐厅信息不是必填项，用户不需要强制确认店铺。
- 前端展示问题：**“这顿饭在哪里吃？”**
- 用户可选择：
  - 附近推荐店铺
  - 在家吃
  - 外卖/打包
  - 公司/学校/食堂
  - 自己填写店名
  - 跳过店铺信息
- 只有用户明确选择某家店或填写店名后，系统才展示该店相关 POI 信息和公开评论摘要。
- 如果用户选择“在家吃”“食堂”或“跳过”，系统只做菜品识别、热量估算、成本估算和健康建议，不展示餐厅口碑模块。
- 如果用户选择“外卖/打包”，可允许用户补充店名、平台或菜品名称，再尝试查询公开摘要。
- 如果用户自行填写店名，系统结合当前城市或定位区域进行搜索，不强行匹配错误店铺。

### 2.8 评论与卫生风险线索

- 可接入地图 POI 和公开可用评论摘要。
- 第一版不接大众点评/美团评论全文，不做爬虫。
- 评论摘要只使用合法可获取的信息，例如：
  - 地图 POI 评分
  - 人均消费
  - 店铺标签
  - 公开搜索结果摘要
- 根据公开信息总结：
  - 口味评价
  - 卫生相关负面线索
  - 服务/环境问题
- 不允许直接判断“地沟油”“食物不干净”。
- 只能表达为：
  - “评论中有人提到卫生问题”
  - “存在卫生风险线索”
  - “仅供参考，无法通过照片确认”

## 3. 推荐技术方案

### 3.1 平台

- 微信小程序。

### 3.2 模型分工

- 千问视觉模型：
  - 菜品识别
  - 坐标框
  - 食材和烹饪方式初步判断
  - 份量初步估算
  - 餐具、锅具、汤底、摆盘等餐型视觉线索
- DeepSeek V4 Flash：
  - 热量推理
  - 菜系与餐型归类
  - 菜品成本推理
  - 营养风险总结
  - 个性化饮食建议
  - 评论摘要总结
  - 前端展示文案生成

### 3.3 地图与评论数据

- 地图 POI 推荐优先使用高德、腾讯位置服务或百度地图。
- MVP 推荐只接一个地图供应商，避免复杂度过高。
- POI 查询流程：
  - 小程序获取定位
  - 后端调用地图周边搜索
  - 筛选餐饮类 POI
  - 返回 3-5 个候选店
  - 用户选择店铺、选择在家/外卖/食堂，或跳过
- 评论摘要推荐使用：
  - POI 自带评分、标签、人均
  - 公开搜索 API 的标题和摘要
  - DeepSeek V4 Flash 做总结
- 不把第三方平台评论爬虫作为 MVP 依赖。

### 3.4 成本数据来源

- MVP 可先使用内置的常见食材成本参考表。
- 成本参考表应至少覆盖：
  - 米饭、面食、豆制品
  - 猪肉、牛肉、鸡肉、鱼虾
  - 常见蔬菜
  - 鸡蛋、奶制品
  - 常见调味和油脂的粗略摊销
- 如果用户选择餐厅或外卖，优先结合：
  - POI 人均消费
  - 店铺类型
  - 城市或商圈
  - 菜品数量和类型
  - 公开摘要中的价格线索
- 第一版不需要接实时菜市场价格 API，避免复杂度过高。

### 3.5 后端职责

- 图片上传与压缩。
- 调用千问视觉模型。
- 调用 DeepSeek V4 Flash。
- 营养基础数据查询。
- 成本参考数据查询。
- 地图 POI 查询。
- 公开搜索摘要聚合。
- 结构化结果校验。
- 不长期保存用户敏感健康信息。

### 3.6 图片标注交互实现要求

- 千问视觉模型返回的坐标框应保存为原图坐标系或归一化坐标，不直接保存屏幕显示坐标。
- 前端渲染时，根据当前图片显示尺寸、缩放比例和平移偏移，将坐标框映射到屏幕位置。
- 图片、坐标框、标签和点击热区必须使用同一套缩放和平移状态，避免出现框与菜品错位。
- 用户修改菜名或删除菜品不应改变其他菜品坐标框。

## 4. 页面与流程

### 4.1 首页

- 拍照按钮。
- 相册选择按钮。
- 健康备注入口。
- 历史记录入口可选，MVP 可不做。

### 4.2 分析中页面

- 显示上传和分析状态。
- 第一版允许等待 10-20 秒。
- 若失败，提示重新上传。

### 4.3 用餐地点选择

- 系统提示：**“这顿饭在哪里吃？”**
- 如果有定位，展示附近 3-5 家餐饮店。
- 同时展示：
  - 在家吃
  - 外卖/打包
  - 公司/学校/食堂
  - 自己填写
  - 跳过
- 该步骤可跳过，不影响菜品识别、热量分析和成本估算。

### 4.4 结果页

- 顶部展示原图和菜品标注框。
- 原图区域支持双指缩放、拖拽平移和点击局部放大。
- 缩放和平移过程中，所有菜品坐标框、标签和点击热区必须随图片同步变化。
- 下方展示：
  - 总热量范围
  - 整桌成本范围
  - 菜系/餐型判断
  - 菜品列表
  - 单菜热量
  - 单菜成本
  - 健康建议
  - 餐厅/评论风险线索，可选
- 支持用户修正菜名或删除误识别菜品。
- 如果用户未选择餐厅，不展示餐厅口碑模块。

### 4.5 菜品详情

- 展示单个菜品的：
  - 识别名称
  - 置信度
  - 估算份量
  - 热量范围
  - 成本范围
  - 可能食材
  - 烹饪方式
  - 营养风险
- 用户修改菜名或删除菜品后，系统应重新计算整桌热量和整桌成本。
- 用户修改菜名或删除菜品后，系统应重新判断整桌菜系/餐型。

### 4.6 健康备注页

- 用户可选择或填写：
  - 糖尿病
  - 控糖
  - 减脂
  - 高血压
  - 忌口
- 默认本地保存。
- 分析时临时发送给后端生成建议。

## 5. 非目标范围

第一版不做以下内容：

- 不做医疗诊断。
- 不判断食物是否含地沟油。
- 不判断食物是否真正不干净。
- 不做医生级营养处方。
- 不做长期慢病管理。
- 不做复杂账号体系。
- 不强依赖多平台爬虫评论。
- 不强制用户确认餐厅。
- 不保证每道菜识别 100% 准确。
- 不保证菜品成本等于真实采购价或真实售价。
- 不接实时菜市场价格和供应链报价系统。

## 6. 验收标准

- 用户上传一张饭菜照片后，能返回至少一个菜品识别结果。
- 多菜场景下，能在图片上展示多个坐标框。
- 用户放大、缩小或拖拽图片时，菜品坐标框仍然对准原图中的对应菜品。
- 用户点击图片局部位置后，能放大查看该区域，且目标框同步放大。
- 每个菜品有名称、热量范围、成本范围和置信度。
- 整桌有总热量范围和总成本范围。
- 整桌有菜系/餐型判断、分类置信度和简要判断依据。
- 火锅、干锅、烧烤等餐型应触发对应的油脂、钠、糖或蘸料风险提示。
- 用户备注糖尿病时，高碳水/高糖/高油菜品能给出谨慎建议。
- 定位开启时，能返回附近 3-5 家餐饮候选店。
- 用户可选择在家、外卖、食堂、自行填写或跳过店铺信息。
- 用户未确认店铺时，不展示伪造或猜测的餐厅评论结论。
- 评论卫生风险只能作为线索，不能直接断言食品不安全。
- 成本估算缺少依据时，应显示“不确定”或低置信度。
- 用户修正或删除菜品后，整桌热量和成本应同步更新。
- 分析失败时有明确错误提示。

## 7. 预算与准备

启动阶段建议准备：

- 微信小程序认证费用。
- 域名和 SSL。
- 云服务器或云开发服务。
- 千问视觉模型 API。
- DeepSeek V4 Flash API。
- 地图/POI API。
- 公开搜索 API，可选。
- 基础营养数据。
- 常见食材成本参考表。
- 隐私政策和用户协议。

MVP 建议先控制在小预算内，重点测试真实照片识别准确率、热量估算质量、成本估算合理性和建议质量。

## 8. 给外包或开发方报价时的砍价点

必须报价的核心项：

- 小程序前端。
- 图片上传。
- 千问视觉识别接入。
- DeepSeek 分析接入。
- 结果页标框展示。
- 热量估算。
- 菜品成本估算。
- 菜系/餐型识别。
- 健康备注。
- 地图 POI 候选店查询。
- 用户选择在家/外卖/食堂/跳过的地点流程。
- 基础后端 API。

可以砍掉或后置的项目：

- 账号体系。
- 历史记录。
- 多平台评论抓取。
- 高级数据看板。
- 复杂会员系统。
- 长期饮食记录。
- 医疗级健康报告。
- 实时菜市场价格 API。
- 供应链采购价系统。
- 精美动效和复杂 UI。

第一版只要求能跑通核心闭环：**拍照、识别、标框、判断菜系/餐型、估算热量、估算成本、建议、可选地点信息**。
